# Stadionhopper data model

This document separates the **current repository shape** from the **target model** needed for the prototype. The files in `Database/` are templates/placeholders today; they are not a populated test dataset.

## Current tables

| File | Current fields observed | Notes |
|---|---|---|
| `Clubs.json` | `club_id`, `name`, `type` | `club_id` identifies a club. |
| `Stadiums.json` | `stadium_id`, `name`, `adress` | The current template spells the address field `adress`; API responses normalize this to `stadium_address`. |
| `Matches.json` | `match_id`, `match_date`, `status`, `stadium_id`, `club_id` | The current template supports one club reference only; the API also accepts `home_club_id` and `away_club_id` when present. |
| `Users.json` | `user_id`, `username`, `created_at` | No password/hash field or session data exists in the current template. |
| `Posts.json` | `post_id`, `content`, `created_at`, `user_id` | `user_id` should reference the author. |
| `Checkins.json` | Not present in the current repository | Add a check-in table when implementing issue #55; do not assume it already exists. |

## Target relationships

- **Club 1 → many Matches** as home/away club (target fields: `home_club_id`, `away_club_id`).
- **Stadium 1 → many Matches** through `stadium_id`.
- **User 1 → many Checkins** through `user_id`.
- **Match 1 → many Checkins** through `match_id`; derive the stadium from the referenced match rather than trusting a client-supplied stadium ID.
- **User 1 → many Posts** through `user_id`.

## Recommended target records

A match should have a stable `match_id`, a valid date/time, a `status`, a `stadium_id`, and club references that exist. A check-in should have `checkin_id`, `user_id`, `match_id`, and `created_at`. A post should have `post_id`, non-empty `content`, `user_id`, and `created_at`. A user should have a stable `user_id`, unique normalized `username`, and `created_at`.

If password authentication is added, store only a password hash generated by an established password-hashing library, never a plaintext password. Authentication/session implementation is outside this document and must be reviewed separately.

## Validation rules

1. IDs must be present and unique within their table.
2. Foreign keys must point to existing records; reject unknown user, match, stadium, or club IDs instead of silently creating records.
3. A check-in's user identity must come from the authenticated server-side session, not from a request body or query parameter.
4. Derive a check-in's stadium from its match. Reject duplicate check-ins for the same user and match, or define a documented idempotent response.
5. Trim post content and reject empty content; derive the post author from the active session if post creation is supported.
6. Treat missing/placeholder values as absent data. Do not convert placeholder templates into fake real-world records.

## Data-file compatibility

The existing templates contain Python-style `None` values and trailing commas, so they are not strict JSON as checked in. The current API has a narrow read-time normalizer for this legacy format. Prefer valid JSON (`null`, no trailing commas) for any new or rewritten data file, and avoid rewriting existing templates as part of unrelated issues.
